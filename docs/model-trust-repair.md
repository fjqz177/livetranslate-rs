## 2. 行为规格

### 2.1 闸门位置（唯一）

ASR 线程装配点：`build_worker_config` 成功（说明清单长度达标）→ **校验闸门** → `ensure_started`（起 worker）。三条装配路径共用此闸门：启动装配 / 待命唤醒装配 / 运行时引擎切换。

- 检查对象：该模型注册表清单的**全部文件**逐个 sha256（whisper 1 个、SenseVoice 2 个、nano/qwen3 各 6 个）。
- 期望值：注册表 `files_sha256`（2026-09-10 起 20/20 全量登记，见 `docs/architecture-v2-improvements.md` §6 whisper sha256 行）。
- 本地自定义模型（whisper 档位填磁盘路径、无注册表条目）**不校验**——无指纹可比，仅保留"能加载"判定，行为与今相同。
- 成本（release 实测 sha2 ≈ 1.5GB/s，Ryzen 9 7945HX）：tiny 0.02s / base 0.04s / small 0.12s / SenseVoice 0.15s / turbo 0.37s / large-v3·nano·qwen3 ~0.7s；冷缓存另加一次磁盘读。

### 2.2 校验不通过的动作

1. **隔离**：坏文件改名 `xxx.corrupt`（不改内容、不删除——保留现场可诊断；同名旧隔离文件被覆盖，数量有界）。
2. **发事件**：`UiEvent::ModelIntegrityFailed { model, fault }`，`fault = ModelFault::Hash { file, expected, actual, quarantined }`。
3. **中止本次装配**：走 `AsrUnavailable`（加载框关闭；运行中切换失败则旧引擎继续工作），**不**进入 worker 启动。

隔离之后缓存探测自然判"缺"——这是"重下按钮不再空转"的机制根（旧实现坏文件顶着正式名，探测认为已缓存，点下载秒报成功却什么都不下）。

### 2.3 修复闭环

- 触发：`ModelFault::Hash`（校验失败）或修复期内的下载失败。
- 动作：自动发起真下载（读设置总线当前 hub/proxy，与用户点按钮同路）。
- 上限：**3 次**（计数在 UI 侧修复状态机）。重试间隔由下载器自身的传输级退避（1s/4s/16s）承担，不引入定时器。
- 用尽：提醒用户——日志 ERROR + 原生通知 + 下载卡失败态；**手动重试按钮永久有效且重置计数**。
- 清零：装载成功（`AsrDevice` 事件）或用户手动发起下载时计数归零。
- 不自动重试的类别：磁盘类失败（需用户清盘）、用户取消。

### 2.4 边界（必须诚实执行的例外）

- **哈希通过但加载失败**：内容与官方指纹逐位一致 → 重下同内容必然同结果，**不自动重下**。发 `ModelFault::Unloadable { detail }`，提醒用户（提供"强制重下一次"的手动入口与换引擎建议）。
  - 该分支的判定依据：加载失败后**复验一次哈希**——不匹配 → 按 §2.2 走 Hash 故障（修复循环）；匹配 → 本分支。
- 上游删档/长期无网：自动重试 3 次后提醒（物理不可达，机制只保证入口永在 + 原因说清）。
- 每次加载多读一遍模型文件：零信任的固有成本（用户已知情，裁决 1）。

## 3. 事件与契约

```rust
// lt-proto（纯新增变体 → 冻结规则加法豁免，PROTO_VERSION 不递增）
UiEvent::ModelIntegrityFailed { model: String, fault: ModelFault }

pub enum ModelFault {
    /// 内容与注册表指纹不符（可修复：隔离 + 重下）
    Hash { file: String, expected: String, actual: String, quarantined: bool },
    /// 内容与指纹一致但加载失败（不可通过重下修复）
    Unloadable { detail: String },
}
```

- 生产端：lt-orchestrator（`trust_gate` / 加载失败复验）。
- 消费端：lt-ui（下载卡 + 日志 + 原生通知 + 修复状态机）。
- 死契约守卫配套：两端齐备，不需白名单（如守卫口径有变以 `scripts/check_dead_contract.ps1` 为准）。

## 5. 评审勘误（同轮实证）

**原评审 B 项"卡流永久挂起、取消不生效"不成立**（2026-09-10 实测证伪）：

- 实验：mock 服务器发完响应头与 10 字节 body 后永久沉默（连接保持）。
- 结果：下载器 **141s 收敛**并返回 `[net]` 失败 = 4 次尝试 ×（30s 逐次读超时 + 1/4/16s 退避）。
- 机理：reqwest 阻塞客户端 `timeout` 为**逐次 read** 预算、默认 30s（`blocking/response.rs` 的 `wait::timeout(body.read(), timeout)`；`blocking/client.rs` 默认 `Timeout(Some(30s))`），非总传输期限——大文件下载不受限，静默对端 ≤30s 判死。
- 处置降级：不再需要看门狗；改为**显式化**（T1：把 30s 写进 `http_client`，避免将来有人"顺手去掉"）+ 回归测试钉住。
- 结论修正：卡流时"取消"最多延迟 ≤30s 生效，下载会话必然收敛，不构成死锁。

同轮其余评审项状态：A（Checksum 不回落 + 文案误导）→ **本包不解**（Checksum 与上游换档强相关，等决策 3 重议）；C（缓存只验长度）→ 本包 §2 根治；D（版本钉死）→ 用户裁决暂不做（§6）；E（镜像 302 落海外 CDN）→ 记录不改。

## 6. 已知失效面（用户已知情，决策 3 的代价）

- **上游同名重传**：注册表哈希过期 → 所有用户校验失败 → 自动重试 3 次 → 提醒。届时处置 = 更新注册表并发版（不做 revision 钉死；若将来上游频繁变动，再议决策 3）。
- **模型加载的零信任只覆盖登记条目**：本地自定义模型无指纹，天然不可验。
- **手动"强制重下"不校验哈希对不上之外的场景**：Unloadable 分支的重下是用户主动行为，仍会过下载期三道校验。
