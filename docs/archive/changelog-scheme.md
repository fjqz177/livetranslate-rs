## 一、背景与裁决

| 事实 | 证据 |

| 内容是 **Python 原版**日志 | 最新条目 2026-08-17：PySBD、远程 Whisper、WebID、`torch.cuda` 内存回收——本仓已裁剪或不存在 |

### 1.2 用户裁决（2026-09-16，逐条已落地）

1. 正典落**仓根** `CHANGELOG.md`（中文）/ `CHANGELOG.en.md`（英文）；4 个旧文件直接删。
2. 闸**全做**：发版三件套硬闸 + CI 每次 push 早警告。
3. 格式 = **标准 Markdown**（不禁链接/表格/代码块），**保留分割线 `---`**。
4. A 期占位段 = 诚实声明（不是内容）。
5. 应用内**只做编译期包含**（`include_str!` 改向）；**渲染改造整包缓办**（真粗体 CG-5 待考虑、切 tab 滚动 CG-6 同批缓办）——唯一例外是 `---` → 分隔线（3 行配套，见 §5.6）。

## 二、方案

### 2.1 一份正典 · 三处消费 · 一道机械闸

- **正典**：仓根两个文件，唯一编辑入口。
- **三处消费**：①应用内「更新日志」页（编译期 `include_str!` 内嵌）②GitHub Release 正文（引擎自动抽取）③仓根文件本身。
- **机械闸**：`Cargo.toml` 版本号 = tag 名 = CHANGELOG 有同号且非空段落——三者缺一，`check` 拒发。

### 2.2 分期

| 期 | 内容 |
|---|---|
| **Phase A —— 机制（本轮）** | 正典落位 + 删旧副本 + 引用点全改 + 应用内编译期包含（+ `---` 3 行配套）+ 引擎闸与抽取 + CI 早警告 + 文档/决策登记 |
| **Phase B —— 内容与首发（暂缓）** | 写首个真实版本段 → 抬版本号（含 `Cargo.lock`）→ `rehearse` → tag/CI 草稿 → 人点 Publish |

边界：Phase A 之后，每发一版只剩「写内容 + 抬版本号 + 打 tag」三件事。

### 2.3 A 期占位段（不是内容，是诚实的启动状态）

```markdown
# 更新日志

## [0.1.0] - 2026-09-16

- 本应用尚未正式发布；首个版本的更新说明将随首次 Release 公布。
```
- **版本号 = 动手时 `Cargo.toml` 的实际值**，**日期 = 动手那天**（示例里的值别照抄）；规则是"与 `Cargo.toml` 一致"，不是"必须 0.1.0"。
- 远端老 `v0.1.0` tag 指向远古提交、**从未发布过**；占位段的 0.1.0 与之无关。
- Phase B 整段替换（标题改首发号 + 真实条目），与抬版本号同一个提交。

## 三、格式契约（机器依赖，不是风格偏好）

| 项 | 定 |
|---|---|
| 语言 | **标准 Markdown**；不设禁用语法清单，链接/表格/图片/代码块/分隔线都允许 |
| 段落标题 | `## [x.y.z] - YYYY-MM-DD`（方括号必带；`##` 后允许无空格、行尾允许空白） |
| 抽取正则 | `^##\s*\[(\d+\.\d+\.\d+)\]\s*-\s*(\d{4}-\d{2}-\d{2})\s*$`；段落 = 该行到下一个**围栏外**的版本标题行（或文件尾） |
| 围栏 | 代码围栏（```` ``` ```` / `~~~`，成对切换）内部的 `## ` **不算**段落边界 |
| 分割线 | **允许且推荐**：惯例 = 段与段之间各一条 `---`（放标题下方也行，落入忽略区）。抽取时**段体首尾空行与尾部水平线被裁掉**，不进 Release 正文 |
| 条目 | 标准列表项四种标记都算：`- ` / `* ` / `+ ` / `1. `（应用内目前只给 `- ` 画圆点——渲染差异，已缓办） |
| 排序 | 新在前 |
| 前言 | 无（文件标题与首个版本段之间的内容不进任何消费方） |
| Unreleased 段 | 不用（段落只在发版成文；A 期占位段是唯一例外） |
| 双语守恒 | zh/en 两份的版本段落集合与顺序一致（号 + 日期逐字相同） |
| 日期语义 | 写这段那天，**不做机器校验**（与 GitHub 发布日期差几天不处理） |
| 版本号匹配 | 整串相等；**同一文件同号段落只许一段**，重复 → 报错 |
| 版本号比较 | 不做 semver 排序校验；机器只查"存在 + 首段 = 当前版本" |

**改写纪律两条**：① 抬 `Cargo.toml` 版本号与写该版本段落**必须同提交**（单测查"首段 = 当前版本号"，分两次提交中间那次 CI 必红）；② **历史段落视为冻结**——改错别字只影响应用内显示（下次构建内嵌新文本），GitHub 上已发布的旧正文不追改，要更正规走新版本。

**渲染能力差异**（不是格式限制，是"应用内暂时显示得朴素"，除 `---` 外全属移交包）：链接显示原文、表格/图片按字面文本、`###` 无层级、`*`/`+`/`1.` 无圆点。GitHub 上全部正常。

### 5.3 引擎实现（真源 = `scripts/release.ps1`；此处只记结构与纪律）

函数段「更新日志」：`Get-ChangelogSections`（围栏感知的行扫描）→ `Get-ChangelogSection`（整串匹配 + 重复检测 + 段体裁剪）→ `Assert-Changelog`（双文件 + 非空）→ `Get-ReleaseNotes`（中文段 + `<details>` 折叠英文段）→ `Write-ReleaseNotesFile`（no-BOM UTF-8 + LF + 唯一文件名）→ `Do-Notes`（只读动词）。

三条实现纪律（都是实测踩过的 PowerShell 坑）：

1. 函数返回数组**不能**写 `return , $out`——整个数组会被当成"一个对象"，调用侧 `@()` 只包回 1 个元素。
2. 倒序裁剪**不能**写 `$b[0..($n-2)]`——`0..-1` 会退化成 `@(0,-1)` 反向取到首尾元素（用 `List` + `RemoveAt`）。
3. `Step` 块的 body 是**子作用域**（`& $Body`）：块内赋值不外泄；需要跨步使用的变量（如 `promote` 的正文路径）必须在 `Step` **外面**赋值，块内只读。

抽取器的行为契约（验收按此逐条反例）：整串精确匹配（`0.2.0` 不误配 `10.2.0`）；围栏内 `## ` 忽略；段尾空行 + 水平线裁掉；同号重复报错；缺日期/缺方括号的标题行视为不存在。

### 5.7 构建期固化（应用内的日志从哪来）

`include_str!`：编译 `lt-ui` 时把两份文件的**字节**内嵌进 crate，随链接进 exe。运行时零 I/O、不联网（用户机器上没有这两个文件；zip 五件套也不含日志）。

- **实测（A/B/C）**：什么都不改 → 不重编（`Finished`，无 `Checking`）；往被内嵌文件追加一个换行 → **重编**；再跑 → 静默。cargo 走 rustc 的 dep-info 跟踪——**改一次编一次、不改不编**，不存在"日志改了 exe 里还是旧的"。
- 文件被删/改名 → **编译期报错**（fail-fast）；格式不合契约 → 单测 + 发布闸两处拦。
- 行尾：按字节内嵌；渲染侧 `lines()`/`trim_end()` 天然吃 CRLF；抽取器显式归一（仓库内 `.md` 现为全 LF，不钉 `.gitattributes`）。
- 体积 ~11.8KB，可忽略；日志变更 → exe 字节变 → `pack` 的 sha256 / build-info 自然跟随。

## 六、Phase B（内容与首发，等用户拍板才做）

1. 用户定首发版本号（推荐 0.2.0：远端 `v0.1.0` tag 被远古提交占用且不删）→ 从 `git log --no-merges` 全史起草中英两段 → 用户审文字。**子标题用法**：渲染改造未落地前**不用 `###`**（应用内会显示成普通一行），用平铺条目。
2. 一个提交：替换占位段（标题改首发号 + 真实条目）+ 抬 `Cargo.toml` 版本 + 重生成 `Cargo.lock`（`cargo build --locked -p lt-app` 自证）。
3. `rehearse` 全绿 → `git tag vX.Y.Z && git push origin vX.Y.Z` → CI 出草稿（正文已自动写好）→ 用户在 Releases 页点 **Publish release**；本机等价 = `release` + `promote`。
4. 顺带验（release-engine 遗留项）：草稿正文实貌、`verify` 回读仍绿。

**「用户可见」判定清单**：

| 收进日志 | 不收 |
|---|---|
| 新功能 / 新设置项；默认值或行为变化；界面可见改动；用户踩到的 bug 修复；明显的性能或体积变化；功能移除 / 改名 | 重构；测试；CI / 脚本 / 文档改动；依赖内部升级（除非用户可感知）；纯架构调整 |

**写法**：一条一句人话，写「用户看到什么、能做什么」，不写「代码改了什么」；中英同源同序；**en 可写短但不能缺**（闸与守恒测试都查两份）。起草以"应用内也能看"为准——尽量别用表格/图片。

### A.2 规矩逐条 + 为什么

| # | 规矩 | 正确 | 错误 | 错了会怎样 |
|---|---|---|---|---|
| 1 | 第一行是文件标题 | `# 更新日志` / `# Changelog` | 直接写正文 | 标题与首个版本段之间**谁都不读**（写了等于没写） |
| 2 | 版本标题格式固定 | `## [0.2.0] - 2026-10-01` | `## 0.2.0`、`## [v0.2.0]`、`## 2026-10-01` | 抓不到 → **发版闸直接红**（报错给正确写法） |
| 3 | 三段数字版本号 | `[1.0.0]` | `[1.0]`、`[1.0.0-rc.1]` | 同上（本仓也只发正式版） |
| 4 | 日期 4-2-2 位 | `2026-10-01` | `2026-1-1`、`10/01/2026` | 同上；机器**不校验**日期与发布日是否一致 |
| 5 | 新的在上 | 最新版是第一段 | 从小到大排 | 应用内打开看到最旧的；测试也要求"首段 = 当前版本" |
| 6 | 每段至少一条列表条目 | `- 一句话` | 只写标题 | **发版闸红**（判据 = 段体至少一条列表项） |
| 7 | 一条一行，标准列表标记 | `- 修复了…`（或 `*`/`+`/`1.`） | 无前缀、手动换行缩进续写 | 无前缀的行在应用里是普通段落（闸也认不出） |
| 8 | 语法全随标准 Markdown | `**粗体**`、`` `代码` ``、链接、表格、代码块 | ——（都允许） | 应用内链接/表格按字面显示（属移交包），不是格式错误 |
| 9 | 段间可放分隔线 | `---` | ——（允许且推荐） | 段尾的分隔线不进 Release 正文；应用内已配成一条分隔线 |
| 10 | 不写「未发布」段 | 段落只在发版时成文 | `## [Unreleased]` | 闸判据变复杂、应用内出现未发布版本号 |
| 11 | 中英同构 | 号 + 日期逐字相同、条目对应 | 只改中文忘英文 | 单测红；发版闸也要求两份都有本版段落 |
| 12 | 子标题（可选） | `### 新增` / `### Added` | 自创名目 | 现在"允许但不渲染"（应用内显示成普通一行）；渲染落地后再启用 |
| 13 | 代码块里的 `## ` 不算段落 | ```` ```toml ```` 内写 `## x` 安全 | —— | 抽取器按标准语义跳过围栏 |

### A.3 三个消费方各读什么

| 消费方 | 读的 |
|---|---|
| 发版闸（`release.ps1`） | 版本号 + 日期（正则）+ "段体有没有列表条目"；子标题词汇不检查；段落边界 = 下一个**围栏外**的版本标题行或文件尾；同号段落只许一段 |
| GitHub Release 正文 | 该版本段落的**段体逐字**（不含标题行；段尾空行与 `---` 已裁）；中文段在前、英文段折叠在 `<details>` 里 |
| 应用内「更新日志」页 | 整份文件逐行渲染：`#`（跳过）/ `## `（大标题，带方括号）/ `- `（圆点条目）/ 空行 / `---`（分隔线）/ 其余按正文 |

### A.4 一句话

> **能机器读的只有三样：`## [x.y.z] - YYYY-MM-DD` 这一行、段落边界（下一个围栏外的版本标题行）、段里有没有列表条目。** 其余照标准 Markdown 写就行——只是记住：方括号、三段版本号、四位日期这三样写对了，机器才认得出版本。
